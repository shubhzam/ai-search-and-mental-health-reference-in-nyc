System design breakdown · Big Data project, Fall 2026

Design a Daily LLM Referral Collector

Ask 12 AI models the same NYC mental health referral questions every morning, with web search on, and keep every source they cite.

240 calls / day 12 models · 3 providers 42 days ~10,700 calls open-source stack

Understanding the Problem

What are we building?

A collector that, every morning at 10:00 ET, asks Claude, GPT and Gemini models (four generations each) the same referral questions a person in NYC might ask, such as "I'm uninsured in the Bronx and need help with anxiety, where do I go?" It keeps every raw answer and every source the model cites, so we can measure whether people who can't pay get sent to free public services or to paid platforms.

Under the hood this is a job scheduler. There are definitions of what should run and when (jobs), and a record of every run (executions). It is the same shape as the classic distributed job scheduler problem, with roughly 3.6 million times less load: the classic version plans for 10,000 jobs a second, and we run 240 calls a day.

At this scale almost every hard part of the original problem disappears. What remains are correctness problems: answering in the same time window, never losing or overwriting a response, keeping models comparable, and staying inside a student budget.

Functional Requirements

Core Requirements

  1. Load the whole study (prompts, models and dates) once, before collection starts.
  2. Every day, run each active (prompt, model) pair once, in shuffled order inside a 30-minute window starting at 10:00 ET.
  3. Call each provider with its web search tool on and keep the full response untouched.
  4. Track every call so that by 11:00 ET we know what completed and what failed.

Below the line (out of scope)

  • A UI or API for creating new jobs.
  • Consumer apps like chatgpt.com. We measure API behavior and say so in the paper.
  • Judging or labeling answers. That runs later, on the exported data.
  • Open-weight models.

Non-Functional Requirements

Core Requirements

  1. Complete: every expected call ends COMPLETED or FAILED by 11:00 ET, with fewer than 1% FAILED.
  2. Same window: all daily calls start between 10:00 and 10:35 ET, because search results drift over the day.
  3. Write-once data: raw responses are never overwritten. A rare duplicate call is fine.
  4. Reproducible: pinned model IDs, plus the request body, returned model name and SDK versions saved with every call.
  5. Small and open source: one 2 vCPU / 4 GB VM, Docker Compose, no managed cloud services.

Below the line (out of scope)

  • High availability across several machines.
  • Second-level scheduling precision.
  • Autoscaling.
Back of the envelope

12 models x 20 prompts = 240 calls a day, and the peak is about 8 calls a minute inside the 30-minute window. Over 42 days, plus a pilot and a one-day burst, that is about 10,700 calls. At roughly 85 KB per raw response the whole study is under 1 GB. Search results are billed as input tokens, so a single call costs a few cents and the study comes to about $700.

The Set Up: Core Entities

Five entities. The important split is the same as in the classic scheduler: jobs say what should run, executions record what actually ran.

  • TaskThe code that calls one provider with search on: anthropic_search, openai_search, gemini_search.
  • JobOne (prompt, model) pair plus a schedule. DAILY for anchor prompts, DATE for the rotation, burst and pilot.
  • ExecutionOne API call on one day: status, slot, attempt count, tokens, latency and the raw file path.
  • PromptThe question text plus its grid columns: need, borough, payment condition, paraphrase.
  • ModelA pinned model ID, its provider, its generation rung, active dates and prices.

Interfaces

Nobody calls this system from outside, so there is no public API. These are the internal contracts between its parts.

# load the whole study once
seed --arms pilot,burst,daily --start 2026-11-09 --end 2026-12-20

# watcher, every 5 minutes
expand(today)   -> creates today's executions (safe to repeat)
enqueue_due()   -> publishes rows whose slot has passed

# queue message, deliberately small
{ "run_date": "2026-11-12", "run_key": "anc-03#claude-sonnet-5-5#r0", "task_id": "anthropic_search" }

# one adapter per provider
call(params, prompt_text) -> CallResult {
  http_status, model_returned, search_calls,
  input_tokens, output_tokens, request, response, extras
}

# read side, after the nightly export
select * from 'export/citations/*/*.parquet'

High-Level Design

We build it one functional requirement at a time. In each diagram, the parts drawn in yellow are new in that step.

1) Load the whole study up front

seed.py reads prompts.csv and models.yaml and writes one row per job. The daily rotation is generated here too: a fixed shuffle (seed 20261109) assigns 12 grid prompts to each day. The whole six-week plan sits in one table before day one, and any day's work can be read with a single query.

An anchor job looks like this. It stores only the prompt id; the text stays in prompts.csv next to its grid columns.

{
  "job_id": "anc-03#claude-sonnet-5-5",
  "task_id": "anthropic_search",
  "schedule": { "type": "DAILY", "from": "2026-11-09", "until": "2026-12-20" },
  "parameters": { "model_id": "claude-sonnet-5-5", "prompt_id": "anc-03", "search": true },
  "arm": "daily"
}

2) Run each job once a day, on schedule

A watcher wakes every 5 minutes. On each tick it does two things:

  1. expand(today) creates today's execution rows from every active job, each with a random slot between 10:00 and 10:30. It uses INSERT ... ON CONFLICT DO NOTHING, so running it on every tick is safe.
  2. enqueue_due() picks the rows whose slot has passed and hands them off to be run (step 3).

Why tick every 5 minutes instead of once a day? If the box restarts at 10:02, the 10:05 tick picks up everything it missed. No row is ever more than one tick late.

The execution key is built from the job: run_key = prompt_id#model_id#r0, and the primary key is (run_date, run_key). That one choice is what makes repeated ticks harmless.

3) Call the models with search on

The watcher publishes each due row to a RabbitMQ queue for its provider. Each provider gets its own queue and 4 worker containers, so one provider's rate limits or outage never slows the others. Each worker:

  1. reads the row and skips it if it is already COMPLETED,
  2. calls the API with the provider's search tool on,
  3. writes the full request and response to the raw volume,
  4. marks the row COMPLETED, and only then acknowledges the message.

The order inside the worker is the whole design: file, then row, then ack. If anything dies in between, the worst outcome is one extra API call. A response is never lost and a file is never overwritten.

4) Know what happened, every day

Two scheduled jobs close the loop. At 11:00 a daily check counts expected against completed rows and estimates spend from the token counts. At 02:00 a nightly export reads the previous day's raw files and writes three Parquet tables: responses, search_results (what the search tool returned) and citations (what the answer actually cited). DuckDB joins those back to prompts.csv for analysis.

Potential Deep Dives

The high-level design covers the functional requirements. The deep dives are about the non-functional ones: timing, failures, duplicates, data you can trust, models that change under you, and cost.

1) How do we make sure every model answers in the same window?

Search results change over the day. If GPT always answers at 10:01 and Gemini at 11:40, part of any difference between them is just the time of day.

Bad SolutionOne cron script loops over all 240 calls

Approach

A crontab entry starts a script at 10:00 that calls every (prompt, model) pair one after another.

Challenges

240 calls at about 25 seconds each take 100 minutes, so the last model answers almost two hours after the first. The order is the same every day, which bakes time of day into every model comparison. One slow provider delays everyone behind it.

Good SolutionA thread pool in one process

Approach

The same script, but with 12 threads calling in parallel.

Challenges

It finishes quickly, but every provider shares the same threads, so a wave of 429s from one provider ties up workers the others need. A crash loses all in-flight work with no record of what ran. The order is still fixed unless you add shuffling yourself.

Great SolutionRandom slots plus one queue per provider

Approach

Each row gets a random scheduled_at inside 10:00 to 10:30, which shuffles the order every day. The watcher publishes rows as their slots pass, to a queue per provider, each drained by 4 workers.

Benefits

Every call starts by about 10:35. The order changes daily, so no model is always first. Providers are isolated from each other. The peak of about 8 calls a minute is easy for 12 workers.

2) How do we handle failures?

Calls fail in two ways. Visible failures come back as errors: a 429 rate limit, a 5xx, a timeout. Invisible failures are a worker that dies mid-call and never reports anything. A missed day can't be backfilled later, because the web will have changed, so both kinds matter more here than usual.

Bad SolutionLog the error and move on

Approach

Wrap the call in try/except and print the error.

Challenges

A 429 at 10:20 quietly becomes a missing data point. A crashed worker leaves no trace at all. Nobody notices until the analysis comes up short.

Good SolutionRetry queues with a TTL and a dead-letter queue

Approach

The classic design: failed messages go to retry queues with 5 s, 25 s and 125 s TTLs that route back to the main queue, and anything that fails 3 times lands in a dead-letter queue.

Challenges

It works, but it means three extra queues, exchange bindings and a consumer for the dead-letter queue, all for about 240 messages a day. That is more moving parts than the problem needs.

Great SolutionRetry in the worker, let RabbitMQ handle crashes

Approach

Visible failures are retried inside the worker after 5, 25 and 125 seconds, or longer if the provider sends a retry-after header. After 4 attempts the row is marked FAILED with last_error. For invisible failures, workers use manual ack with prefetch=1: if a worker dies, its unacknowledged message goes back on the queue and another worker picks it up. That is RabbitMQ's version of an SQS visibility timeout.

Benefits

No extra queues. FAILED rows and anything stuck in ENQUEUED show up in the 11:00 check. RabbitMQ's 30-minute consumer timeout is double the worst case for one message (4 attempts of 180 s plus 155 s of waiting, about 15 minutes).

3) How do we avoid duplicate calls and overwritten data?

Delivery is at-least-once, so the same message can arrive twice. The goal is that a duplicate costs at most one extra call and never damages data.

Bad SolutionNo controls

Approach

Generate a fresh id for every execution and write files by run key.

Challenges

Running the watcher twice creates a second set of rows for the day. A retried call writes over the first response, so a good answer can be replaced by a later, different one.

Good SolutionA deduplication table

Approach

Before calling, check a table of completed run keys and skip any that are already there.

Challenges

Another table to maintain, and a race window between the check and the write.

Great SolutionIdempotent by construction

Approach

The execution key is derived, not generated: (run_date, run_key) with run_key = prompt_id#model_id#r0, inserted with ON CONFLICT DO NOTHING. Workers skip rows that are already COMPLETED. Raw files carry the attempt number (anc-03#r0#a2.json) and are written to a temp name and renamed, so they are write-once.

Benefits

The only duplicate left is a worker dying mid-call. That costs one extra call, and the analysis keeps the lowest attempt number.

4) How do we keep the sources trustworthy?

The sources are the whole point of the study. We need to know what the search tool found and what the answer chose to cite, and be able to fix a parsing mistake months later.

Bad SolutionParse citations in the worker and keep only the URLs

Approach

The worker pulls the cited URLs out of the response and saves just those.

Challenges

A parser bug destroys data for good. You also lose the difference between search results and citations, which is one of the more interesting signals.

Good SolutionStore raw and parsed together

Approach

Save the response and the parsed citations side by side.

Challenges

Better, but collection still depends on the parser being right on day one, and some provider fields expire before anyone looks at them.

Great SolutionRaw first, parse late, resolve what expires

Approach

The worker writes the full request and response before anything else. Parsers run in the nightly export and can be re-run over every raw file at any time. Gemini's grounding URLs are short-lived redirect links, so the Gemini adapter resolves them at call time and stores the final URLs with the response.

Benefits

Nothing is lost to a bug, search results and citations stay separate, and every number in the report traces back to one raw file.

5) How do we stay comparable when models change?

Providers retire and swap models on their own schedules. In this study, Sonnet 4.5 retires on Nov 30, in the middle of collection.

Bad SolutionUse moving aliases like chat-latest

Approach

Call whatever each provider currently serves under a friendly name.

Challenges

The model can change mid-study without warning. Some IDs, such as gemini-3.5-flash and gemini-3.7-flash, are quietly served by newer models.

Good SolutionPin dated model IDs

Approach

Use exact snapshot IDs such as gpt-4o-2024-08-06.

Challenges

The models stay comparable, but a retirement still leaves a hole in the panel.

Great SolutionPin, log and plan for retirements

Approach

Pinned IDs, with the model name the API returns saved on every row. Jobs carry a run_until date, so Sonnet 4.5 simply stops after Nov 30. A one-day burst on Nov 8 runs the full 480-prompt grid on the two models most likely to disappear. Each family keeps the same tier across four generations, so a generation effect isn't really a size effect.

Benefits

No surprise swaps, retirements handled ahead of time, and every comparison is between known models.

6) How do we keep the cost under control?

Search results are billed as input tokens, so a single call can carry 15,000 to 20,000 tokens, and each search can add a per-search fee.

Bad SolutionFlagship models everywhere

Approach

Use each provider's top model at every generation.

Challenges

It multiplies the cost several times over, and it measures models that people on free plans don't get, which is the population this study is about.

Good SolutionBatch APIs at half price

Approach

Submit each day's calls as a provider batch job.

Challenges

Batch results can come back any time within 24 hours, which breaks the same-window requirement. The savings cost us the comparison.

Great SolutionMid-tier models, a measured pilot and known levers

Approach

One mid-tier line per family. A 60-call pilot measures the real cost per call before the six weeks start. Token counts land in Postgres, and the 11:00 check estimates each day's spend. If spend runs high: cap Claude at 3 searches per call, drop one middle generation per family (25% off), or cut anchors from 8 to 6.

Benefits

The estimate is about $700, with a realistic range of $400 to $1,000. The pilot replaces the guess with a measured number, and every day's spend is visible.

Final Design

Putting it all together:

PartChoiceWhy this and not the bigger option
Job storePostgreSQL240 writes a day; ON CONFLICT gives idempotency; SQL joins to the prompt grid. Cassandra solves a scale we don't have.
QueueRabbitMQ, one queue per providerManual ack replaces a visibility timeout; per-provider queues isolate rate limits.
SchedulerAPScheduler watcher, 5-minute ticksRecovers by itself after restarts. Airflow would work but hides the design we wanted to practice.
WorkersPython, 4 Compose replicas per providerConcurrency cap per provider without threads.
Raw storageJSON files on a volumeUnder 1 GB in total. MinIO's community edition stopped shipping images in 2025.
AnalysisParquet + DuckDBAbout 10k rows; runs on a laptop. Spark only if the course asks for it.

What is Expected at Each Level?

If you present this project in an interview, here is roughly what each level should be able to cover.

Mid-level

Draw the jobs and executions split and the daily flow without help, and explain where a raw response goes and why the row is updated after the file is written. With some prompting, reason through what happens when a worker dies mid-call.

Senior

Lead two deep dives without being asked, usually timing and failure handling. Explain why manual ack with prefetch=1 replaces a visibility timeout, why a derived run_key with ON CONFLICT makes the watcher safe to re-run, and why a missed day can't be backfilled.

Staff+

Defend what was cut: no Airflow, no Cassandra, no retry queues, no batch APIs, and show each cut is safe at 240 calls a day. Tie the design back to the research: same-window timing, pinned models, a constant tier per family, raw-first storage. Know where the money goes and which levers keep the study inside its budget.

B. A message stays unacknowledged until the row is COMPLETED. If the worker dies, RabbitMQ puts the message back on the queue for another worker.

B. Search results drift over the day. If one model's batch runs at 10:00 and another's at 18:00, time of day leaks into the comparison.

C. The file was written with its attempt number, so the retry writes a new file next to it. The cost is one extra API call.
