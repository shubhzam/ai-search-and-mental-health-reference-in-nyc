# Automatic persistence and recovery

The import plan covers saved historical files. Pilot, scheduled manual batches and supplemental batches also need a durable dispatch gate. They use the same PostgreSQL transaction lock as the importer and the same filesystem lock as historical collection. Reconcile existing ledgers before issuing new requests. Calculate shared provider spend from persisted estimates, provisional charges, outstanding reservations and the separate $0.01 Gemini allowance. Reserve $0.50 before dispatch and reject projected spend above $9. The $1 buffer absorbs estimate uncertainty within the $10 project cap. Provider invoices remain authoritative.

A live attempt uses a stable source path under `data/live/`. A committed PostgreSQL reservation identifies the expected raw response path. Write provider bytes there exclusively and sync them before persisting the terminal row. Store a small receipt with the observed HTTP status and finish time when available. For recovery after a crash between raw write and receipt, parse the saved body and leave the missing finish time null. Keep unreadable bodies and uncertain costs linked to the attempt and retain the reservation. An outstanding pre-dispatch reservation blocks further requests until recovered or reconciled. A database failure after capture leaves the raw bytes and reservation intact and ends the run.

`recover-collection` reads saved bytes and settles pending attempts without credentials or provider requests. If an outcome has no saved bytes, the reservation remains for operator reconciliation against provider records. A crash before dispatch and a crash after dispatch but before capture can leave the same evidence. Never automatically reissue either request. A retry requires an explicit plan with a new attempt key and a reference to an existing failed execution.

`batch --plan FILE --batch-id ID` replaces temporary runners for reviewed supplemental, continuation and retry plans. Normal scheduled batches can still be built from a planned date. Live plans are saved before dispatch. Docker uses the host `data/` directory and the ignored `.env` for credentials. Historical batch plans remain local and their fingerprints and matching entries are stored with imported attempts.

Python 3.13, PostgreSQL 17 and existing locked SDKs remain in use. See [transaction locks](https://www.postgresql.org/docs/17/explicit-locking.html), [Psycopg transaction contexts](https://www.psycopg.org/psycopg3/docs/basic/transactions.html), [Python file operations](https://docs.python.org/3.13/library/os.html) and [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/).

Use `batch --planned-date DATE --prompt-id ID --batch-id ID --write-plan FILE` to generate a supplemental plan for review. A plan may select the existing 8,192-token Gemini setting with `--gemini-output-tokens 8192`. Commit happens only when the reviewed file is passed back with `--plan FILE --live`. Each capture receipt includes the observed dispatch and receipt timestamps. A missing receipt can leave both timestamps unknown.
